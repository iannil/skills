# 版本发布与依赖协同

从当前请求确定目标仓库、版本策略、渠道、环境与已授权操作。已有明确发布授权直接推进；只要求准备方案或本地打包时不推送、发版或部署。自动模式不扩大授权范围。

## 固定发布对象

检查每个仓库的分支、提交与未提交改动，确定哪些属于本次发布。读取项目现有 CI、版本配置、插件协议和下游锁文件；沿用版本规范，不猜新标签或覆盖已发布标签。

建立最小发布表：组件、源版本、目标版本、产物、消费方、兼容条件、依赖顺序和恢复方式。核对主程序与插件组合、平台产物和下游实际解析版本，不能只改 README 的版本号。

## 复用验收证据

已有测试证据仅在提交、配置、环境与验收范围仍适用时复用；打包、依赖或构建参数变化后补相应检查，不机械重跑无关测试。

从可控的干净环境验证安装或启动路径，确认发布包含必要资源、默认配置可用且无本地凭据。开源交付按需读取 [开源交付检查](references/opensource-readiness.md)。

构建后记录产物与源码对应关系、校验值和版本输出。本机编译成功、安装成功、远程发布成功分别验证。

## 按依赖发布并核实

遵循项目机制执行打包、指定文件提交、推送、标签、发布附件或镜像，以及下游版本更新。独立组件可按需要并行，但依赖消费必须等提供方产物确实可用。不要把整个工作树未审查改动一起提交。

对异步 CI 等待最终状态，核对发布资产、镜像摘要、下游构建和目标环境版本；命令退出零或返回工作流链接不等于部署完成。失败记录最后成功步骤，重试前先读取远程状态避免重复创建。

跨仓库部分成功时报告已发布部分与仍受阻部分。不自动撤销已发布版本或破坏性回滚数据；根据事先恢复方案及已有授权处理。不可逆迁移需具体恢复策略，不能假定每次部署都能直接降级。

## 交付与状态

分别列出“代码已实现／验收通过／本地安装／产物发布／下游升级／线上生效”，附实际证据和未完成原因。使用项目既有状态结构，不因新增技能擅改编排器 JSON 协议。

功能验收交给可用的 `engineer-qa`，单纯状态冲突可交给 `engineer-reconcile`；不存在这些技能时仍可依据当前证据完成发布，不把安装整条技能链作为前提。
