# 已有系统的核心识别与精简

先用当前用户目标描述最短业务闭环，再沿真实入口查依赖。按职责而非目录名区分：核心决策、必要支撑、可替换适配、已失效功能和证据不足部分。认证、持久化、恢复等非核心职责可能仍是完成目标的必要条件。

为每个精简候选记录使用方、运行入口、配置开关、数据兼容性和移除影响；未搜索到引用不证明动态加载或外部消费者不存在。行数和依赖数量是线索，不是删减目标。

优先沿已有接缝隔离变化，把替换点设计到实际需要的边界。不要为“以后可插拔”新增通用插件平台，也不将每个函数包成接口。给出保留、合并、剥离、替换和待确认项及理由。

方案按可验证的小步排序，明确每步的行为不变量、兼容策略和回退条件。分析任务不删代码；执行任务在授权范围内修改并验证，保护未提交改动和数据。改变需求范围必须明确呈现，不能用删功能使验收通过。

输出核心闭环、职责与依赖图、精简决策表和实施顺序；现状失真时先核准证据，必要时使用可用的 engineer-reconcile。
