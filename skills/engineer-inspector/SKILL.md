# 代码与架构审查

基于当前用户目标、适用项目约定和可追溯证据评审。CONTEXT.md 是设计依据之一，不能覆盖用户已明确接受的新决定。只要求审查时不修改实现，授权修复时完成具体改动及复核。

## 取得范围和当前意图

确认提交或分支基准、暂存与未暂存改动及相关新文件。空 diff 不自动回退最近提交。没有 Git 时依据用户指定文件和实现入口检查，并说明无法证明的变更历史。

读取当前需求、相关设计和必要调用方。没有蓝图时仍可检查实际调用链、契约与可观察行为；将推断的架构意图标为推断，不伪造原始约束。文档与代码冲突时先查新决定，再判断实现偏离、文档过期或证据不足。

## 按影响检查

- **契约与数据**：接口、模型、配置及迁移是否破坏调用方或已存数据。核心文件变化本身不是违规；检查需求依据、兼容策略及迁移后果。
- **职责与复杂度**：新增抽象是否解决实际变化点，边界是否减少耦合，依赖是否必要。层数、行数和单实现接口只是定位线索，不单独构成缺陷。
- **状态与失败**：错误处理、取消、重试、并发和恢复是否保持业务不变量；仅检查任务涉及的风险，不附加无关全面加固。
- **术语与界面**：同一概念的命名和行为是否一致，前端是否符合当前设计。合理的新概念可同步文档，不因词汇表尚未登记就阻塞。
- **文档与配置**：部署命令、权限建议、API 示例、版本与默认值是否会误导使用。纯注释按实际影响缩小审查，不一律直接通过。
- **验证证据**：现有测试是否真正覆盖本轮风险，有无只断言实现细节的测试。未增加测试文件不等于未验证；执行与覆盖率判断交给可用的 `engineer-qa`，或遵循项目测试约定。

发现需精简架构时可使用 `engineer-architect` 的精简模式；发现状态与资料全面失真时可使用 `engineer-reconcile`。小问题直接处理，不强制加载其他技能。

## 形成可行动发现

每项给出位置、触发条件、具体影响、证据与最小修改建议。区分已证实缺陷、待验证怀疑和非阻塞建议。不要把个人风格偏好列为必修，也不要把一次测试失败直接推为架构错误。

检查修复与直接调用方；有行为变化时取得对应测试证据。无法证明的风险保持开放，不编造测试结果。文档更新不能掩盖未获接受的行为变化。

## 判定和推进

- **PASS**：本次审查范围没有未解决的阻断发现。静态审查通过不等于功能测试或生产运行通过。
- **NEEDS_FIX**：存在有证据的阻断问题，给出修复范围。
- **UNVERIFIED**：关键意图或证据不足，明确缺什么及可继续的部分。
- **REBUILD**：仅为兼容旧调用方的重规划建议，需说明为什么局部修复不合适；不是失败次数触发的自动行为，不授权重置工作树。

模式只控制输出详略与已有授权内的推进；不自动删除、硬重置、缩减目标或混入用户改动提交。报告复用项目位置，无约定时可写 `.agents/inspection-latest.md`，包括范围、依据、发现、验证和剩余事项。达到请求的审查目标后停止，不无休止扩大范围。

## ⚙️ 模式选择

normal 展示必要结果；auto 在已有授权内继续；silent 减少过程输出。三种模式使用相同验收判据，并保留失败、未验证和恢复信息。
