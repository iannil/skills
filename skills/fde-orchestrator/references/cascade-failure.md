# 级联失败处理 / Cascade Failure Handling

依赖传播用于保护尚未满足的契约，不是放弃需求的机制。必需失败项持续进入修复与复验，独立任务可继续。

## 依赖类型

| 类型 | 含义 | 示例 |
|------|------|------|
| hard（默认） | 上游契约必须满足，下游依赖部分才能执行和验收 | API 依赖 User 表及迁移 |
| soft | 下游可独立实现；若原交付仍要求上游能力，整体完成仍需补齐验证 | 页面可先渲染，通知联动留待上游完成 |

已有 schema 不支持类型字段时在蓝图/摘要注明，不自行更改依赖数组格式。

## 传播规则

| 上游事实 | 下游行为 |
|----------|----------|
| DONE 且证据适用于当前代码 | 可执行；下游仍须自身验收 |
| 旧降级记录、DONE 但缺证据 | 核对契约和实际产物；缺失视为未验证，不能按完成放行 |
| BLOCKED 或用户已授权 SKIPPED | hard 依赖项保持 BLOCKED，并在现有原因字段记录根因和 cascade；独立部分可先推进 |
| BLOCKED / SKIPPED + soft 依赖 | 可继续独立工作，记录上游限制和待补集成；不能豁免原验收 |
| IN_PROGRESS / TODO | 依赖部分等待；其他无冲突任务可继续 |

递归沿 hard 依赖传播。`BLOCKED (cascade)` 仅是人读说明，不是新的状态枚举；不新增 DEGRADED 状态。SKIPPED 仅代表明确不适用或已授权排除，不计作原需求完成。

## 修复与解除

1. 保存根因、证据、尝试结果及下一动作到现有 issues/summary，引用 CONTEXT.md / REQUIREMENTS.md 委托约定。
2. 在授权内修复根因并复验原失败项和受影响集成范围。失败次数不意味着重建、缩成 happy path 或必须用户兜底。
3. 根因通过后逐项复核下游：其他依赖是否满足、是否存在自身失败、已有验证是否仍适用。只有纯级联阻塞才恢复可执行状态；不能一律改 TODO 或直接 DONE。
4. 调整 hard/soft 前证明替代契约可用。产品范围或不可妥协项变化须有授权；更改标签或用户要求“继续”本身不能代替技术验证。

每一个必需集成缺陷都进入修复复验，不按数量设门槛。无可执行修复时保留未完成并推进独立任务；只对真实价值取舍或授权缺口升级。

## 影响与升级摘要

```text
根因：M2 [失败事实及证据]
已尝试：[措施、结果、仍未解决的原因]
影响：M3 hard 依赖被阻塞；M5 的独立页面工作仍可继续
推荐：[下一方案、代价及风险]
待决定：[仅真实价值取舍/授权缺口；没有则直接推进]
下一动作：[根因修复、复验及下游解除条件]
约定引用：CONTEXT.md / REQUIREMENTS.md [章节]
```
