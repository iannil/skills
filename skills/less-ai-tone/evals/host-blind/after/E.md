# 缺货反馈与替换退款：业务说明（节选）

本说明覆盖社区团购里「团长发现缺货 → 向供应商反馈 → 供应商响应 → 替换或退款落地」这一段闭环。读者是后续架构与实现，不要求在此展开全站需求。

## 角色旅程

团长的核心旅程从提货或分装时开始。他清点到某 SKU 少件，或外包装破损不能交到用户手中，就在团长端发起缺货反馈，写清自提点与活动场次，写明 SKU 和短缺数量，并上传一张现场照片。他关心的是今晚还能不能给邻居一个可执行答复：是换规格、换邻近批次，还是原路退款。工单号好不好看并不重要。

供应商的旅程从收到反馈开始。采购或仓配值班人要在约定时限内确认：能补货、能替换近效期或近规格商品，或确认无法履约。确认替换时必须给出替换 SKU、数量与到达自提点的预计时间。确认退款时必须给出退款范围（该团长名下未分发份数）。供应商不直接改用户侧展示文案，但必须让团长在端上看到可转发的结论。

平台值班主任只在超时、争议和金额异常时介入：例如供应商超时未响应，或替换商品过敏原与原商品冲突，又或退款金额超过该场次团长可退余额。介入的结果是升级工单，而不是悄悄改状态。

## 业务事件

关键事件按发生顺序理解：缺货已登记、证据已提交、供应商已签收反馈、供应商已确认补货、供应商已提出替换方案、团长已接受替换、团长已拒绝替换、退款已发起、退款已到账、反馈已关闭、反馈已升级。技术上的消息投递成功不是业务事件。团长是否已把结论告诉用户，才是闭环是否完成的观察点。

事件之间有依赖。没有「证据已提交」，供应商可以签收，但不能结案为「团长误报」。没有「团长已接受替换」，库存预占不得转成出库。退款已到账之前，缺货反馈不得关闭，否则对账会把未退金额吞掉。

## 状态机（缺货反馈单）

```
草稿 → 已提交 → 供应商处理中 → 待团长确认替换 → 已替换履约 → 已关闭
                              ├→ 退款中 → 已退款 → 已关闭
                              ├→ 已升级
                              └→ 已驳回（证据不足，可回到草稿）
```

合法转移必须可验证。已提交后团长可撤销，但仅当供应商尚未签收。供应商处理中超时，系统自动升到已升级，并通知值班主任。待团长确认替换若被拒绝，流转到退款中，而不是回到供应商处理中死循环。已关闭是终态。终态后的更正走新的「售后更正单」，避免同一主键被反复改写。

## 验收口径（人话）

团长提交含照片的缺货反馈后，供应商在时限内给出替换或退款结论。团长接受替换则自提点能收到替换件，拒绝则对应份数退款到账，且反馈单关闭。任一时刻团长打开详情，都能说出「现在卡在哪一步、下一步谁动」。超时未响应会进入已升级，而不是停在供应商处理中假装还有人看。

这段需求的边界也要写清：它不覆盖用户端的自动退款文案策略，不覆盖供应商主数据新建 SKU 的完整流程，只要求替换 SKU 必须已存在且对团长可见。缺货原因里的「运输损坏」与「仓内短少」要可区分，因为后续赔付归属不同，但本阶段只需把原因字段留下，不在此展开财务分摊规则。
