# 构建性能优化

先记录要缩短的等待：干净构建、冷启动、热构建、单文件保存到页面可访问，不能用其中一项替代其他项。读取真实构建命令、输入规模、插件、环境和既有性能目标。

## 建立可比较基线

保留基线版本与工作树状态。在同一机器、同一输入和可比后台负载下测量，说明缓存是否预热；做足以观察波动的重复运行，报告中位数及离散程度。网络、下载和生成时间单独说明，避免把偶然缓存命中当优化收益。

同时记录输出正确性与内存、磁盘、CPU 等实际相关资源。先对基线重复输出比较，识别时间戳等非确定项并解释排除规则，不能直接忽略所有不一致文件。

## 用测量选择改动

通过 profiler、阶段计时或调用统计定位重复解析、模板执行、序列化、I/O、插件启动和失效范围。一次验证一个可归因的假设；不因“并行更快”而盲目并发，也不为局部收益先重写整个架构。

缓存键应覆盖影响结果的输入、依赖、配置与工具版本；检查内容变更、删除、改名、依赖变化和语言切换。开发监听检查事件合并、丢事件、并发修改与输出发布时序。

## 正确性与收益一起验收

比较增量结果与同版本干净全量构建，检查文件集合及内容；覆盖本轮影响的删除、重命名、聚合页面、模板、配置或插件变更。只比较共同文件会漏掉应删除的旧文件。

运行与改动相关的测试、竞态检查或压力重放。结果不一致先解决原因；无稳定收益则撤回本轮实验，不覆盖用户原有改动。记录缓存或并行带来的内存、磁盘与维护代价。

## 交付

报告测量命令、环境、样本数、优化前后结果、正确性证据、资源变化和未解决瓶颈。区分源码已修改、本机已安装、下游已升级与已发布；优化请求不自动包含发布。没有可重复证据时交付瓶颈结论，不宣称达到理论极限。
